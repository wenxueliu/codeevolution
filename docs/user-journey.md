# CodeEvolution 用户旅程

## 1. 目标

CodeEvolution 的核心旅程是：

> 用户把一个或多个代码仓接入工作台，手动生成可信的分析快照，再围绕业务、架构、开发、测试和运维问题进行探索、解释、问答与验证。

系统不把“打开页面”视为一次解析。用户明确触发分析后，系统才读取目标仓库并生成不可变 Snapshot；后续知识、调用树、解释和跨仓结果都应绑定到 Snapshot 或 Graph View。

## 2. 主旅程

```text
准备代码仓
  ↓
注册代码仓 / 组织服务
  ↓
手动运行分析
  ↓
生成 Repository Snapshot
  ↓
创建稳定 Graph View
  ↓
浏览结构知识
  ↓
深入调用链与业务解释
  ↓
进行跨仓拓扑、影响分析和流程追踪
  ↓
代码问答、审计和 UI 测试
  ↓
代码变化后重新分析并比较结果
```

## 3. 阶段旅程

| 阶段 | 用户目标 | 用户动作 | 关键反馈 | 产物 |
|---|---|---|---|---|
| 准备 | 让系统能够分析代码 | 安装 CodeGraph CLI，确认目标仓可读 | 可检查路径、Git 仓库和现场改动 | 可分析代码仓 |
| 接入 | 将仓库纳入工作台 | 添加服务名称和绝对路径 | 显示仓库成员、路径和索引状态 | Scope / Repository Member |
| 分析 | 获取某一时间点的代码知识 | 选择成员并点击“运行分析” | 按成员显示初始化/同步图谱、冻结、分析、发布等阶段；可取消或重试失败成员 | Analysis Run / Snapshot |
| 组合 | 查看多个仓库的整体关系 | 选择成员并创建当前 View | 固定成员与 Snapshot 的组合 | Graph View |
| 探索 | 理解代码结构 | 浏览 API、模块、实体、测试、依赖等分区 | 展示统计、列表和证据位置 | Knowledge Report |
| 深挖 | 理解一个功能如何工作 | 展开端点、调用树和时序图 | 展示调用路径、前端调用和源码位置 | Call Chain |
| 解释 | 将代码翻译成业务语言 | 手动生成 API 功能解释或业务规则 | 展示异步状态、覆盖率和解释快照 | Explanation Snapshot |
| 追问 | 快速获得代码事实 | 询问类、方法、调用方或历史 | 返回受控查询操作及答案 | Chat Answer / Audit Log |
| 验证 | 将分析结果转成回归测试 | 录制 UI 操作、添加检查点并回放 | 展示 DSL、接口记录和运行结果 | UI Test Recording |
| 更新 | 让结果反映新代码 | 重新运行分析并刷新 View | 新结果发布，旧结果仍可查看 | New Snapshot / New View |

## 4. 角色旅程

### 4.1 产品经理：从接口理解业务

```text
进入代码仓
→ 查看 API 契约
→ 筛选目标接口
→ 展开调用链和时序图
→ 生成 API 功能解释
→ 阅读业务流程、规则和副作用
→ 形成需求、验收标准或影响判断
```

重点关注 API 目的、请求响应、业务步骤、权限、校验、状态变化和外部副作用。

### 4.2 架构师：从单仓结构理解系统拓扑

```text
注册多个服务
→ 检查各服务健康度
→ 创建多仓 Graph View
→ 查看服务拓扑及每条依赖的证据链
→ 追踪 HTTP / MQ / Redis / gRPC 流程
→ 分析服务变更影响
→ 检查分层违规、热点和外部依赖
```

重点关注服务依赖、跨仓调用、影响范围、边界违规、共享资源和核心实体。

### 4.3 开发者：从问题定位到代码证据

```text
进入目标服务
→ 查找 API、类或方法
→ 查看调用方和被调用方
→ 定位源码文件和行号
→ 使用代码问答查询关系
→ 查看规则或解释
→ 修改代码
→ 显式检查现场改动并重新分析
→ 在旧/新 Snapshot 或 View 间切换（跨快照 diff 待实现）
```

重点关注入口、调用路径、前端调用位置、变更影响和结果来源的 Snapshot。

### 4.4 测试人员：从测试缺口到可回放用例

```text
查看测试缺口
→ 找到未覆盖的生产函数或 API
→ 查看调用链和业务规则
→ 进入“代码问答 → UI 测试”
→ 配置测试目标
→ 录制用户操作
→ 添加可见文本 / URL / 接口响应检查点
→ 停止并保存
→ 回放并查看结果
```

### 4.5 运维人员：从依赖和健康度识别风险

```text
发现或注册服务
→ 检查 CodeGraph 和索引状态
→ 查看外部依赖、配置消费和权限模型
→ 查看消息队列、Redis、数据库依赖
→ 追踪跨服务流程
→ 评估服务故障或变更的传播范围
```

## 5. 异常旅程

### 5.1 首次运行分析（自动初始化 CodeGraph）

```text
用户注册仓库
→ 选择成员并运行分析
→ 系统自动执行 CodeGraph init（已有图谱时执行 sync）
→ 按成员展示初始化/同步、冻结、分析和发布进度
→ 成功后发布 Snapshot
→ 失败时显示失败阶段、原因和仅重试该成员的入口
```

### 5.2 多仓部分失败

```text
用户一次分析多个仓库
→ A 成功、B 失败、C 未变化
→ A 发布新 Snapshot
→ B 保留旧 Snapshot
→ C 保持原 Snapshot
→ 用户单独重试 B
```

一个成员失败不应回滚同一次 Run 中其他成员已经发布的成功结果。

### 5.3 LLM 未配置

```text
用户浏览结构知识
→ 点击业务解释
→ 系统提示需要 LLM
→ 用户打开“LLM 设置”
→ 保存配置并测试连接
→ 返回知识中心重新生成
```

没有 LLM 时，API、模块、实体、测试缺口等结构知识仍应可用。

### 5.4 Snapshot 与现场代码不一致

```text
用户在旧 View 中执行“检查现场改动”
→ 系统展示 Snapshot 采集时间、来源及 unchanged / source_changed / check_failed
→ 用户发现现场代码已变化
→ 用户主动重新分析
→ 创建新 View
→ 在旧/新结果间切换；跨快照差异对比待实现
```

“当前结果”“最近一次失败尝试”和“现场代码是否变化”需要明确区分。

## 6. 用户成功标准

- 用户能明确知道当前查看的是哪个仓库、哪个 Snapshot 和哪个 View。
- 用户能从一个 API 入口追踪到完整调用链和源码证据。
- 用户能区分结构化分析结果与 LLM 推导结果。
- 分析失败时，用户知道失败仓库、失败阶段和下一步重试动作。
- 多仓分析能说明依赖边的证据，而不是只显示服务名称。
- 测试人员能将一个业务旅程录制、保存并回放。
- 仓库发生变化后，用户可以主动生成新结果而不破坏旧结果。
- 失败、取消和现场代码在采集期间变化均不会替换 current Snapshot。
- 多仓拓扑、影响和流程查询明确绑定 Graph View；单仓知识、调用链和解释明确绑定 Repository Snapshot。
